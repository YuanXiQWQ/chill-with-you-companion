# 起手与回归：我们和游戏的区别是「插入」

游戏里她的动作是**从头到尾由游戏演**：`start → loop → end` 一整族播完，结束段本身就是游戏写好的"回到待机"路径。
我们是**插进去**的一段，所以要自己负责两头：

- **起手**：从她此刻的姿势进，不是从"我们都不知道多久以前"的姿势进。
- **回归**：演完把身体交回去，而且交回去的那一刻不能看得出接缝。

## 一、被证伪的做法（记下来，别再走一遍）

### ① 交回"开演前的快照"

`baseGameRot` 是插入时缓存的姿势。用它当回归目标，等于交回一个**过期姿势**：
她的待机一直在推进，快照是静止的，淡出落在死姿势上，放手瞬间就跳。

实测：`return ... dist=0.0deg`（距离被自己刚写下的值污染）、`handoff dev=22.58deg`。

### ② 直接改游戏正在跑的待机（`Animator.CrossFadeInFixedTime`）

想法最好，但在我们手里的 API 下不成立：`CrossFadeInFixedTime` 认的是**状态名**，
我们只导出到 **clip 名**；名字对不上就静默无事发生，游戏照跑自己的状态机。

实测 8 次采样全部 `held=False`，且游戏一直在自己的 idle 序列里推进：

```
idle swap: -> anim_break_tea_base_loop
@1.5s … @10.5s  clip=anim_break_novel_base_loop  held=False
```

顺带发现：游戏的待机是**状态机**，会自己切 `tea_sub_unique001_start → loop → end → tea_base_loop`。
所以"持久接管 idle"会和它打架，不是好方向。

### ③ 固定时长收回

`ReleaseMs=300` 对点头够用（差 5°），对站起来（差 100°+）就是"被扫回去"。

## 二、现在的做法

回归目标 = **游戏正在跑的那段待机**，而且**每帧重取**：

```csharp
exitValid = CaptureGamePose(exitRot);       // 每帧：让 Animator 当场求值再读
q = Quaternion.Slerp(exitRot[i], q, kOut);  // 淡出追着一个移动的目标
// 最后一帧再把姿势精确写成 exitRot，交接差归零
```

归还时长按首帧量到的真实距离给：

```
exitRelSec = clamp(0.30 + maxDeg / 180, 0.30, 0.90)
```

`dist` 必须**先存我们的输出、再让游戏求值**才量得准；顺序反了就是拿游戏刚写下的值跟自己比，恒为 0（踩过）。

## 三、实测（游戏内）

| 动作 | 距离 | 归还时长 | 交接差 |
| --- | --- | --- | --- |
| `break_tea_sub_drink_end` | 80.4° | 747 ms | **0.00°** |
| `break_yawn_1_end` | 107.0° | 898 ms | **0.71°** |
| `story_base001_sub_nod` | 107.2° | 895 ms | **0.00°** |
| `wild_leavechair_*_start` | 92.4° | 813 ms | —— |

交接差 ≤ 0.71° 意味着放手瞬间看不见接缝（1° ≈ 手指粗细的偏移）。

## 四、还欠的一件事

「把本来的待机换成更适合衔接的待机」在**游戏侧**做不到（见 ① ②），能做到的等价物在**编排侧**：

> 三段式家族必须把 `_end` 段演完 —— 那正是游戏自己写的"回正"路径。

目前 `planSequence` 已经会展开 `start → loop×n → end`（日志里能看到 `_end` 在播），
所以收尾姿势会往本层待机收敛，而不是停在半路。

剩下的偏差是 `push` 指标本身：它量的是"离待机的偏移"，而 `plan` 量的是"段内运动幅度"，
两个不同的量放在一起比没有意义（`yawn push body=107.0` 对 `plan body=0.2` 就是这个原因）。
下一步要么统一量纲，要么把 `push` 只当"是否真的动到了那根骨头"的布尔判据。
