# 知识库制作

给一个主题建库，做到三件事：**查得到、说得准、不串味**。

- **查得到** —— 检索能命中正确的块，而不是命中了别的文档。
- **说得准** —— 每条事实有出处，版本名这类硬信息以官方原文为准。
- **不串味** —— 库内容走独立 prompt 段落，不进对话历史、不进长期事实、不被模型当成"亲身经历"。

---

## 0. 开工前必答的三问

| 问题 | 为什么要问 | 影响 |
|---|---|---|
| 这库给谁用？ | 角色扮演参考 vs 工作助手查询，`role` 写法完全不同 | 角色用「聊到就按这个口径」，助手用「这是权威资料」 |
| 覆盖到哪个版本 / 时间点？ | 新版本会推翻旧结论，库不写边界就会被追问到崩 | 写进 `role` 和每篇文档开头 |
| 有没有沙箱通道？ | 验证必然要反复问同一句，直接走正常对话会把"不知道"灌进历史 | 没有就先建，见 §6 |

---

## 1. 来源分级

四个等级，**A 直接用，B 交叉用，C 标注，D 只当线索**。

| 级 | 定义 | 判定方法 |
|---|---|---|
| **A** | 官方一手 | 域名为官方、页面标题即正式名、作者挂官方职位 |
| **B** | 高可信媒体 | 转载官方公告、标注"据官方"，但可能有转述误差 |
| **C** | 百科 / 有编辑审核的社区 | 维基、萌娘、Fandom、官方 wiki、百科 |
| **D** | 社区讨论 | 问答站、论坛、视频标题、帖子 —— **只作线索，不作依据** |

**A 级源的识别技巧**（比记域名可靠）：

1. **页面标题就是答案**。版本更新说明的标题形如 `X.Y版本「正式版本名」版本更新说明`，标题本身即权威。
2. **作者栏**。官方博客类站点若作者挂的是项目组职位（如"主策划"、"Lead Game Designer"），正文可当 A 级引用。
3. **商店页编辑推荐**。应用商店的"编辑推荐 / 开发者撰文"栏位文案由官方提供，短但准确，适合取角色定位、版本标语这类**原文级**表述。
4. **社媒官方号**。官方投稿账号的长文与官网同级。

**B 级源的正确用法**：拿它**定位**是哪一版、有哪些新内容，再回 A 级源确认标题与关键设定。B 级正文里的错别字、活动名、光锥名**一律不要照抄**。

## 2. 多方复核

不是"多找几个链接"，是**对每个关键事实问：这个说法最不可能错的形式是什么**。

### 2.1 三级复核

| 事实类型 | 要求 |
|---|---|
| **硬标识**：版本号↔版本名、产品型号、API 名、标准编号 | **必须 A 级**。找不到 A 级就不写 |
| **重大设定**：世界观核心规则、关键身份揭示、结局走向 | **A 级，或 ≥2 个独立 B 级一致** |
| **性格 / 描述性内容** | C 级以上即可，只写"能不能聊得起来"的层面，不复述台词 |
| **传闻 / 剧透** | 不采信，单独列进"未采信"清单 |

### 2.2 冲突处理

两家打架时：

1. 找 A 级原文，**标题和正文都以官方为准**。
2. 官方也没说 → **不写**，或写"官方未明确"。
3. 只有社区在传 → 进"未采信"表，并在正文对应位置**显式标注**这是传闻。

> **实测案例**：某游戏 4.7 版本名，三家媒体转载成「此刻，群星尽付笑谈」，官方公告标题与另一家报道均为「此刻，**将**群星付之一笑」。差一个字，语序完全不同。**版本名这种硬标识必须回官方标题核。**

### 2.3 最容易混的两类东西

- **设定 vs 机制**。官方可能确有「把某类角色宣告为令使」的**战斗机制**，社区却传成「某角色被册封为令使」的**剧情**。两者字面接近、性质完全不同。**遇到"某个名词同时出现在机制和剧情里"，先确认它属于哪一侧。**
- **同名不同人**。外形相似、名字相近的两个角色会被混成"同一人的两个身份"。核对时看**官方是否在同一段文字里并列提到两者**——并列出现即证明是两个人。

### 2.4 复核台账

单独一篇文档记 `事实 → 等级 → 出处 → 核对结论`，并单列"**未采信**"表。这篇文档有两个作用：

- 给未来的自己留证据，避免重复查。
- **让它参与检索**——角色被问到传闻时能答"这个官方还没确认"，而不是"不知道"。

## 3. 文档写作：chunk 友好

知识库按固定字数切块（默认 `CHUNK_TARGET = 320`，重叠 40），**切完块之间没有上下文**。所以写作要按"被切碎也成立"来设计。

### 3.1 四条硬规则

| 规则 | 反例 | 正例 |
|---|---|---|
| **标题不带冗余前缀** | `# 崩坏：星穹铁道 · 宇宙与星神` | `# 宇宙与星神` |
| **每行自包含** | 表格里只写 `4.7 \| 此刻…` | `**4.7「此刻，将群星付之一笑」**：2026-11-11 上线，首位可玩星神` |
| **不要依赖"上一节"** | "如上所述，祂是……" | "阿哈是欢愉星神，……" |
| **重要内容前置** | 版本表按 1.0→4.7 正序 | **倒序**，最新版在最前 |

**为什么标题要去前缀**：库名已经说明了主题。如果每篇标题都带主题词，任何含主题词的查询都会先命中所有标题块，把真正的正文块挤出 top-k。实测中版本表因此掉到第 4 位、被 `maxChars` 截断，角色答"不记得"。

**为什么表格要改列表**：表格会被拦腰切断，"4.7"这一行可能落在下一个块里，而那个块看起来只是一堆符号。**改成每行一个完整句子的列表**，切在哪里都无损。

### 3.2 版本类信息的写法

```
# 版本索引（速查）

主题名 + 版本名对照表，更新至 X.Y。倒序排列，每行自包含。问「XX 版本叫什么」就查这里。

最新版本是 **4.7「此刻，将群星付之一笑」**（2026-11-11 上线）：一句话说清这一版干了什么。
**4.6「月升之前，与兽共舞」**：一句话。
……

**三条速记**
- 3.x 是什么篇章
- 4.x 是什么篇章
- 最新版的关键事件

**常见误记**
- 4.7 不是「XX」，官方写的是「YY」。
```

**第一段就要把"问版本名就查这里"写出来**，这段会跟标题一起进第一个块，命中率最高。

### 3.3 `role` 字段

`role` 是**能力包描述**，会单独进 prompt，告诉模型"这个库能答什么、边界在哪"。写三句：

1. 聊到这个主题时按这里的口径：列举能覆盖的方面。
2. 这个主题和"我"的关系（若是角色扮演：能不能当写作参考、别当原创）。
3. **版本边界**：涉及版本时以文件里写的范围为准，范围外不要硬编。

## 4. 导入

dsh-chill-with-you-companion 的接口（端口按侧车实际端口，默认 `10723`）：

```text
BASE = http://127.0.0.1:10723

# 列出所有库
GET  /chill/v1/kb

# 建库（name 必填，role 强烈建议一起给）
POST /chill/v1/kb          {"name":"…","role":"…","note":"…"}

# 加文档（name + text；也可 raw body + x-doc-name 头）
POST /chill/v1/kb/<libId>/docs   {"name":"…","text":"…"}

# 检索自测
GET  /chill/v1/kb/search?q=<词>&k=5

# 删库（重建前先删，否则同名建两个）
DELETE /chill/v1/kb/<libId>
```

**导入脚本的幂等写法**：先查同名库，存在就删重建，再逐篇导入。否则反复跑会产生 `崩坏：星穹铁道`、`崩坏：星穹铁道 (2)` 这类副本，检索时互相稀释。

**上限**：单文档 40 万字、单库 500 篇。正常主题用不到。

## 5. 验证

**不要只测"检索有没有返回"，要测"答得对不对"**。

### 5.1 三层验证

**第一层 · 检索排名**

```bash
node -e "
(async () => {
  for (const q of ['版本名','核心概念','某个角色','某个组织']) {
    const r = await (await fetch('http://127.0.0.1:10723/chill/v1/kb/search?q=' + encodeURIComponent(q) + '&k=2')).json();
    const h = (r.hits||[])[0];
    console.log(q.padEnd(14) + ' -> ' + (h ? h.docName + ' (' + Number(h.score).toFixed(1) + ')' : '无命中'));
  }
})()
"
```

**判读**：top-1 不一定是"最该命中的那篇"——BM25 会因为词频和文档长度把相关但通用的段落排前面。**只要 top-5 含正确文档就算合格**，因为拼装取 5 条。

**第二层 · 拼装检查**

模拟真实拼装（同样的 `k` 和 `maxChars`），看**最终进 prompt 的到底是哪几篇**：

```bash
node -e "
(async () => {
  const q = '你的问题';
  const r = await (await fetch('http://127.0.0.1:10723/chill/v1/kb/search?q=' + encodeURIComponent(q) + '&k=5')).json();
  let used = 0; const parts = [];
  for (const h of (r.hits||[])) {
    const body = h.text.replace(/\s*\n\s*/g,' ').trim();
    if (used + body.length > 2600 && parts.length) break;
    parts.push(h.docName + '(' + Number(h.score).toFixed(1) + ')');
    used += body.length;
  }
  console.log(q + '  =>  ' + parts.join(' | ') + '   [' + used + '字]');
})()
"
```

**这一步能抓出"检索命中了但被预算截断"的问题**——前几条把 `maxChars` 吃光，真正需要的第 4 条根本没进去。

**第三层 · 沙箱联调**

走**隔离通道**问，不写历史、不改状态（见 §6）。看回答是否用上了资料，以及命中详情。

### 5.2 覆盖度

按**篇章 / 类别**各抽一题，不要只测同一个主题。一库七篇至少测：版本、世界观、势力、剧情、角色、术语、传闻边界各一题。

---

## 6. 沙箱通道：为什么必须有

验证知识库必然要**反复问同一句话**。走正常对话时：

1. 每轮都写进 turns（聊天记录）；
2. 最近 `memoryTurns`（默认 12）轮会作为历史进 prompt；
3. 模型看到自己上几轮说"不知道"，会**继续照着说不知道**。

**于是三次之后，"不知道"就成了她在这件事上的"既有立场"，再怎么改库都没用。** 这不是知识库的问题，是历史污染。

**隔离的最小集**（dsh-chill-with-you-companion 的 `sandbox` 选项）：

| 行为 | 正常 | 沙箱 |
|---|---|---|
| 带最近对话历史 | 是 | 否 |
| 写 turns | 是 | 否 |
| 提炼长期事实 | 是 | 否 |
| 滚动摘要 | 是 | 否 |
| 改状态计数 | 是 | 否 |
| 人设 / 角色设定 / 知识库 | 是 | 是 |

**注意**：只做"不提炼事实"是不够的。如果 `appendTurn` 还在写 turns，历史照样污染。**必须连 turns 一起跳过。**

**已经有污染了怎么办**：清 turns 文件 + 重启进程（内存态也要清）。清之前备份。

## 7. 六类已知坑

按**症状**查。

| 症状 | 根因 | 处理 |
|---|---|---|
| 查到了但答"不记得" | 库内容被塞进「**长期记忆**」段落，模型当成"亲身经历"，回忆里没有就说不记得 | 单独成段，标题写「**参考资料（查证过的事实）**」，并放进**记忆段之后** |
| 同上前提下，改成"参考资料"仍不答 | 标题太软 + 段落太靠前，被当成可选附件 | 加「**不是记忆，是外部资料；说到相关的事就直接讲出来**」；位置放记忆段之后 |
| 检索有结果，但正确那条没进 prompt | 前几条把 `maxChars` 吃光 | 提高 `maxChars`，或改文档让关键信息前置 / 每行自包含 |
| 任何查询 top-1 都是同一篇 | 各文档标题带相同主题前缀 | 去掉前缀，库名已经表明主题 |
| 表格类内容命中率差 | 表格被 chunk 切断，行与表头分离 | 改**每行自包含的列表**，关键内容按重要度**倒序** |
| 同名库检索被稀释 | 导入脚本不幂等，建了多个副本 | 导入前先 `DELETE` 同名库 |
| **符号/数字类关键词查不到**（`0+1`、`+`、`/`、`A→B`） | 切词正则只认字母数字串和 CJK bigram，`0+1` 被劈成单字符后丢弃，查询 token 只剩「是啥」「意思」这类虚词 | 文档里把这类词写成**带虚词的完整句**：「0+1 是什么意思：前面的数是星魂，后面的数是专武叠影」 |
| **别名/外号查不到本体** | 表写成「本名 → 外号」，切块后外号那行不带本名 | 表改成**双向自包含**：`- **点刀哥** = 刃（刃字拆成一点一刀）`，外号在前、本名紧跟 |

**排查顺序**：先看**拼装**（第二层验证）→ 再看**段落位置与标题**（前两行）→ 最后才怀疑检索算法。绝大多数"查不到"都不是算法问题。

## 7.5 语言层：资料的说法要和用户群体的说法一致

知识库最容易忽略的一层不是事实对不对，是**说话的调子对不对**。

**症状**：查得到、答得准，但听起来像在念官方公告。「该角色命途为欢愉，属性为量子」「进行跃迁获取」「当期概率提升角色为」。真实用户说的是「阿哈是欢愉量子」「抽」「这期 up 的是」。

**根因**：资料全部从官方公告和媒体稿抄来，**用词体系就是官方那套**。检索命中什么，模型就照着什么说。

**做法：单独建一篇「口径 / 黑话」文档**，不要试图在每篇正文里改词——正文要保持事实精度，语言层单独一篇。

这篇要含：

| 块 | 内容 |
|---|---|
| 名词简称 | 用户怎么叫这个东西（简称、绰号、缩写） |
| 操作动词 | 官方词 vs 口头词（跃迁/抽、获取/搞到） |
| 圈内术语 | 只有内部人才懂的量化说法（保底/歪/0+1/毕业面板） |
| 别名表 | 每条双向自包含，见坑表 |
| **说话对照表** | 左列「官方腔（别这么说）」、右列「玩家腔（这么说）」—— 这一块效果最直接 |
| 易混清单 | 名字相近的两个东西，显式写「是两个人，别混」 |

**验收方式**：不要问「XX 是什么」，要问**用户会怎么问**——「牢景是谁」「我今天抽卡歪了」「这期 up 是谁」。她答得上来说明口语层进去了；答的时候自己用外号，说明不只是读懂而是会说了。



## 7.6 时效层：同一件事的多种说法要显式排队

资料天然是**不同时间的快照**。官方公告、媒体转述、社区考据、旧攻略会同时躺在库里，模型取到哪条全看词频，于是经常用一句过时的话回答现在的问题。

**光靠提示词「以最新的为准」不管用**——模型没有时间概念，它只看得到文本。**必须把时间关系写出来。**

### 做法：一张显式的时效表

单独一篇文档，四张表：

| 表 | 收什么 | 例 |
|---|---|---|
| **硬标识纠错** | 名字、编号、日期这类有唯一正确答案的 | 版本名被媒体写错、活动名写错、型号写错 |
| **设定随时间变化** | 状态类事实：篇章进度、角色身份、封印状态 | 「某篇已完结」「某人成为可玩角色」「某灾害已解封」 |
| **已被推翻** | 明确不能再用的说法，逐条 ❌ | 「还在更新」「刚开篇」「只是背景板」 |
| **还没定论** | 只有社区在传、官方没表态的 | 传闻身份、未公布名单、未上线内容 |

每行都要带：**事实 / 旧说法 / 当前有效 / 依据**。

**「旧说法」这一栏不能删**。留着有两个用：被追问「不是说是 X 吗」时能接住，以及解释为什么改了。删掉的话，用户拿着旧说法来问，模型只会说「不知道」。

### 时间判断的三把尺

一条消息够不够新，看三样齐不齐：

1. **日期** —— 官方公告和媒体稿带发布日期，社区帖常常没有。
2. **版本号 / 版本标识** —— 写清是哪个版本说的。
3. **有没有被后一条覆盖** —— 同一件事两条说法，默认后出的有效，**除非后出的来源更差**（官方说了 A，之后只有社区传 B，还是 A）。

### 代码层能做什么，不能做什么

给检索加**版本号倾向**是可行的，但**力度必须很小**：

- 斜率 `0.03/版本`（4.7 对 3.0 约 ×1.05）—— 只做微倾斜。
- **同分裁决**才是主战场：分差在 3% 以内视为并列，并列时版本新的先说话。
- **别用大的全局系数**。实测把斜率设成 `0.10` 时，「某概念是什么」这类问题的 top-1 被整体推向版本索引（那篇版本号最密），相关性直接崩。

加权的依据只能从**正文里出现的版本号**取，不要用文件时间戳——重导一次所有文档时间戳就一样了，那个维度是假的。

**还有两个坑**：

- 切词正则会把 `3.0`、`4.7` 拆成单字符再丢弃，于是「3.0 版本」只能靠「版本」二字去撞，永远命中标题块。**分词时要单独保留 `\d\.\d` 这类整体**。
- 长文档里多个版本挤在一个块，切完就分不开。**版本类内容按版本单独起 `##` 小节**，靠标题分节把它们切开。

### 验收：给它一个错误前提

别问「X 是什么」，要**带着旧结论去问**：

- 「4.7 是不是叫『某错误名字』」→ 应答「不对，官方是『正确名字』」
- 「某篇还在更新吧」→ 应答「已经完结了，X 版本收尾」
- 「某传闻身份就是某人吧」→ 应答「官方没说，只能说有这个说法」

**能纠正错误前提，才说明时效层真的进了库里**；只是答对正面问题不算。

### 时效表什么时候更新

时效表不是建完就不管的，它是**唯一需要跟着外部世界变的文档**。三个触发点：

1. **新版本 / 新公告出来** —— 立即加一行，把上一版的「当前有效」降级成「过时说法」。
2. **用户问到一个你答不上的时间点** —— 说明表里缺一段，补上，别让同样的问题问第二次。
3. **发现同一个问题两次答案不一致** —— 库里出现了两条互相矛盾且都没标时间的说法，回去给它们各加日期。

**自查办法**：随便挑五个「当前有效」的条目，问自己「这条是什么时候的」。答不出来的那条就是隐患——它没有日期锚，读者（和模型）无从判断新旧。

### 怎么发现库里已经过时

不靠记忆，靠症状：

- 回答里出现「目前」「正在」「刚刚」这类词，但事实早已结束 → 库里有未标时效的状态描述
- 用户说「不是早就……了吗」 → 对照时效表，旧的没标 ❌
- 同一个问题换个问法答案就变 → 两条说法并存且都没标时间

**状态类事实（完结 / 上线 / 解封 / 换人）最容易腐坏**，比数字类更容易。数字写错了会被发现，状态过期了没人察觉，只会一直错下去。
### 时间口径：用文件的修改时间，别用正文里手写的日期

手写的「核对至：2026-11-14」有个致命问题：**改了三处只改一处日期，剩下两处还在骗人**。而且它靠自觉，不自觉就永远是对的。

**可靠做法**：库里存**源文件的 mtime**，界面显示「X 天前更新」。导入时把 `statSync(file).mtime.toISOString()` 一起传进去，库里 `ageDays` 由它算出来。

正文里的日期仍然有用——人读、以及说明内容覆盖到哪个版本。但**判断新鲜度只看 mtime**，两者分开存，不要互相顶替。

**时间是记录，不是闹钟**。别做成「7 天黄、30 天红」的过期告警——知识本来每天都在变，标签天天见只是制造焦虑，用户会学会无视它。

中性显示一行「上次同步 X 天前」就够。**什么时候跟外面同步是人的决定**，不是系统的催促。按钮的语义是「我现在想跟世界对一下」，不是「你这儿过期了」。

**按钮点了要产出东西，不能只是显示一个数字**。每次点击生成一份带时间戳的任务文件，写清「要查什么」「查到之后怎么改」，交出去就能执行。否则这个按钮只是仪表盘，不是工具。

### 更新闭环：检查 → 检索 → 改原文 → 重导

**库不自动改写自己**。让它自己改，等于让模型用自己的过期知识更新自己的知识库——越更新越错。

正确四步：

1. **检查**：从「版本索引」类文档的章节标题（`## 4.7「...」`）推出当前版本，再推出**下一代**（4.7 → 4.8），生成查询建议。
   **不要全文扫 `x.y`** ——「4.8 起再补」「1.5 倍伤害」都会被算进去，推出的下一代版本号直接错。
2. **检索**：交给能联网的一方逐条查。**这一步必须是外部检索**，不能靠模型记忆。
3. **改原文**：改 markdown 源文件，不是改库里的切片。切片是派生物，改了下次重导就没了。
4. **重导**：跑导入脚本，mtime 自动刷新。

**「该查什么」比「哪条过期」值钱**。全量扫状态词能得到几百行明细，没人看得完。真正有用的是三五条具体查询：`{主题} {下一代版本} 版本 更新`、`{主题} 最新版本 公告`。

**哪些行算「会过期」**：

| 收 | 不收 |
|---|---|
| 含「最新 / 尚未 / 还没 / 即将 / 预计」 | 单纯出现版本号（历史版本号是事实，永不过期） |
| 含「已完结 / 已上线 / 已实装 / 可抽 / 已解封」 | 表中的固定对应关系（版本名、角色名） |
| 含「改动 / 调整为 / 改为」 | 世界观设定、术语定义 |
| 日期 + 状态词同时出现 | 只有日期（发布日期不会变） |

判定用白名单词表，别用「含数字就算」——那会把整张表都扫进来。
## 7.7 社区内容补全：官方资料之外的半个世界

只抄官方资料的库有个通病：**事实都对，但没法聊天**。用户聊的是梗、外号、共识、争议，官方一个字都不写。

和 §7.5 的分工：**7.5 讲「怎么说话」（用词体系），7.7 讲「收什么内容」（去哪找、怎么取舍）。**

### 补什么：三档

| 档 | 内容 | 缺了会怎样 |
|---|---|---|
| **必补** | 简称、外号、黑话、量化说法、圈内动词 | 听不懂用户在问什么（「点刀哥是谁」「0+1 啥意思」） |
| **该补** | 名场面、梗、玩家共识、公认评价、争议点 | 只能一问一答，接不住话，像个查询接口 |
| **慎补** | 传闻、剧透、主观评价、节奏争议 | 要标来源和置信度，当事实写会翻车 |

### 去哪找（按可用性排）

| 源 | 类型 | 怎么用 |
|---|---|---|
| 百科的「用语与梗」类条目 | C | 编辑审核，覆盖最全，**梗的由来写得清楚**，首选 |
| 攻略站（17173 / 9game / 游民） | B/C | 外号大全这类合集最省事，但**错别字多，必须逐个回官方订正** |
| NGA / 贴吧 / 米游社 | D | 判断「什么是共识」用——同一个说法反复出现、没人反驳，就是共识 |
| 视频标题 / 短视频 | D | 只作线索。标题党多，正文常常没依据 |

### 一个梗能不能写进去

三条全过才写：

1. **至少两个独立来源** —— 同一篇被转载多次不算两个
2. **说得出由来** —— 为什么这么叫。说不出由来的多半是临时硬造，过两个版本就没人用了
3. **不是纯主观评价** —— 「某角色强度高」会过时，「某角色被叫某某」是事实

### 怎么写

- **一行一个，自包含**（切块会打散，别依赖上下文）
- **别名双向**：外号在前、本名紧跟，否则外号那行切出去就不带本体
- **梗要带由来**：只写「X 叫 Y」不写为什么，模型只会干巴巴报名字；写清由来它才能自然地用
- **显式区分「官方设定」和「玩家说法」** —— 混着写，模型会把玩梗当事实讲

### 最常见的三个错

1. **抄错字**。攻略站把「镜流」写成「静流」、「希儿」写成「希尔」，照抄就进库了。**每个名字回官方核一遍**。
2. **抄过时梗**。几年前的叫法现在没人用了。**优先取近一年的合集**，并按 §7.6 标时效。
3. **把玩梗当设定**。「A 是 B 的老婆」是玩梗，「A 和 B 是官方配对」是编的。前者可以写进去（标明是叫法），后者不能写。

### 衍生概念：游戏外围长出来的东西

社区内容其实有三层，混在一起写会出事：

| 层 | 例 | 怎么处理 |
|---|---|---|
| **游戏内设定** | 命途、星神、势力、地名 | 按事实写，要出处 |
| **玩家叫法** | 外号、黑话、量化说法、「乐子人」 | 按事实写，**标明这是叫法不是设定** |
| **二创生态** | 同人图文、语C、表情包、MMD、手书 | **单独一节，明确标「非官方」** |

**第三层最容易被忽略，但它恰恰是用户日常在聊的东西**。缺了这层，聊到「你在语C吗」「这个表情包谁做的」就接不上——只能干巴巴地讲设定。

**写法：不点名具体作品，只写生态结构**。具体作品会过时、会得罪人、也难以核实；结构是稳定的：

- **语C**（语言 cosplay）：扮演角色对戏，有专门的群和圈子
- **表情包**：主要来自哪几个角色
- **二创主阵地**：哪个平台（B站 / 米游社 / 微博）
- **官方对二创的态度**：承认还是否认 —— 通常是「不承认也不否认」，这条要说清

**必须显式写的一句**：聊到同人设定时，默认它和官方设定是两回事。不写这句，模型会把二创当正史讲。

### 梗的三条边界

1. **梗当叫法讲，不当设定讲**。「某星神是乐子人」是玩家说法，「祂的行动准则是制造乐子」才是设定。
2. **由来说不清的梗不主动提**。玩家自己也在考据，说错了比不说更尴尬。写到库里的每一条都要能说出为什么这么叫。
3. **争议不复述**。角色强度、剧情评价、抽卡建议这些，玩家各有立场，转述哪一边都会得罪另一边。**换成问对方怎么看**。
### 验收

问**用户会怎么问**（「牢景是谁」「这期 up 是谁」），看两件事：

- **答得上** —— 读懂了口语层
- **回答时自己也用** —— 不只是词典，是真会说了

只满足第一条是查询接口，两条都满足才算进了语言。
## 8. 交付

建完库顺手做三件事：

1. **原件归档**。把 markdown 源文件存到交付区，别只留在库里——库里是切片，改起来不如改原件再重导。
2. **登记交付清单**。写清库名、篇目、块数、来源分级结论、踩过的坑。
3. **留导入脚本**。参数化主题名和目录，下次换个主题直接改两行。
